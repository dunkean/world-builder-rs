## Proven findings (from the code and math)

**1. The "shear 0.60 cap" limits `strength`, not the actual shear.** `coast.rs:68-71`: for each twist, dθ/dz = strength · `noise_1d`′. The quintic fade's slope peaks at 1.875, and neighbouring lattice values can differ by up to 2, so the peak shear is 0.60 × 3.75 ≈ **2.25**. On the axis equator the tangential shear is r²·dθ/dz, so that bound is reachable. The map is still a bijection, because each twist is an area-preserving rotation that depends only on z. But the local distortion is about 3.75× what the comment says, and it compounds over 34 twists.

**2. With the defaults, most bands sit at the cap, so they follow H=1, not H=0.68.** 0.55·0.30·2^(0.32i) ≥ 0.6 once i ≥ 5.83. With R=1.737e6, res=128 and spacing 0.25 there are 17 bands (`band_count`), and bands 6–16 all have strength 0.60. Displacement there scales with wavelength (H=1). At `coast_detail_ratio=1` every band from 1 up is capped. So `coast_detail_ratio` mostly affects bands 0–5, and fine-scale roughness doesn't depend on it.

**3. A hidden regular pattern: each twist makes straight, parallel stripes when zoomed in.** Each twist's displacement depends only on z = a·p and points along the small circles around its axis. At scales much smaller than the coarser bands, the earlier warps are locally affine, so this band's field is a 1D function of one linear coordinate: straight stripes. Two axes per band means a two-direction plaid at each octave. Both twists in a band share one `frequency` (`coast.rs:80`), so the two stripe sets have equal spacing. The axes are seeded and isotropic, so this isn't tied to cube faces (the orientation test confirms that). It is still directional, regular texture, which is exactly what you see at high zoom.

**4. The value noise has a fixed lattice rhythm.** `noise_1d` blends lattice values with a quintic fade, so its slope is exactly zero at every integer lattice point. Shear therefore vanishes on small circles spaced exactly 1/f apart in z, giving a strong spectral peak at the lattice spacing. Between lattice points the profile is a monotone S-curve with no extra detail, which reads as smooth steps. This plausibly adds to the "smooth shoreline" look. Near each of the 34 axis poles the stripes become concentric rings with ρ_k ∝ √k, but displacement goes to zero there (∝ r), so the effect is weak.

**5. Invertibility, stability and determinism check out.**
- Rodrigues rotation about `a` keeps z unchanged, so the inverse reverses the order and negates the angle (`coast.rs:91-94`). This is exact apart from rounding.
- The rounding error in z after a rotation is about 2e-16, which gives an angle error of at most 2.25 × 2e-16. That is stable, consistent with the 1e-12 test.
- Normalizing once at the end is fine.
- `WarpKey` covers every input `CoastWarp::new` reads: seed, resolution, radius, spacing and ratio. The function is pure and evaluates in a fixed order, so results are the same across threads, camera and LOD on one platform.
- No seed collisions within a world: XOR-ing with 104729 flips bit 16, which pushes it outside the band-seed range 0xc0a57..0xc1df1. The axis and offset salts are distinct.

**6. Topology is preserved.** Every twist is a homeomorphism of the sphere, so the composition is too. Land and sea connectivity of `reconstruction(q)` can't change, and the warp never changes the sign of the height.

**7. Confirmed: this warp can't remove coarse grid erosion.** The largest displacement in band 0 is R·0.165/(96·j) ≈ 2.5–3.5 km. The worst-case geometric sum over all bands is roughly 8 km, and typical values are much smaller. A cube-grid cell at res 128 is about 21 km. So the total shift is at most about 0.4 of a cell and usually around 0.1. That bends channels slightly but can't break up the grid pattern; fixing that is upstream, in the erosion and channel-support work the other agents are doing.

## Performance risks
- **Proven:** every `remap`/`inverse` evaluates all bands at every LOD, which is your identity requirement. With the defaults that's 34 twists per call, each costing two `hash64` calls, a `sin_cos`, a `floor`, and a dot and cross product. That's probably around 1 µs per sample (estimated, not measured), and on the order of 0.1 s per 65k-vertex tile for the warp alone. `river_geometry` adds one `inverse` per cell, about 98k cells, which is acceptable.
- **Hypothesis:** at coarse LOD the sub-metre bands are evaluated but alias below the sample spacing. That costs time and may cause a little shimmer.
- **Hypothesis:** if one thread alternates between two configs (for example a preview world and the main world), `CoastWarp::new` rebuilds on every switch. Each rebuild is cheap (17 bands), but it would thrash.

## Hypotheses to verify
- **Native vs wasm mismatch:** `world-viewer` builds a cdylib for wasm32. If it calls `coast::remap` in wasm, `sin_cos`/`powf` from Rust's wasm libm may differ by a few ulp from native libm, so native and wasm results wouldn't be bit-identical. Your thread-identity test can't catch this.
- **Frequency jitter can leave gaps:** with 0.85–1.2 jitter, the ratio between adjacent bands ranges from 1.42 to 2.82, so roughness can be uneven from one octave to the next.

## Suggestions (not applied)
These all keep the warp invertible because θ still depends only on z:
- Use 1D gradient noise or several summed phases per twist instead of value noise, to remove the lattice plateaus.
- Give each twist its own independent frequency jitter.
- Use 3–4 axes per band so there's no two-direction plaid.
- Fix the comment, or rescale the cap, so it refers to the real maximum shear (strength × 3.75).
